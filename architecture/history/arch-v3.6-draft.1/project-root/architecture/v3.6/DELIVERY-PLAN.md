# GameGen 架构交接与增量计划 V3.6

版本：`arch-v3.6-draft.1`。关联：[总架构](ARCHITECTURE.md)、[契约](CONTRACTS.md)。本文件规定下一步怎么验证、如何进入开发及谁负责回答问题；不把计划写成已完成结果。当前交付只有架构文档，没有新增产品或研发程序代码。

## 1. 当前阶段与前序交接

当前工作为 architecture 阶段的详细设计。前序输入为产品经理已落地的 V3.5 完整需求、四份补充需求、状态清单、V3.6 助手扩展及当前产品清单。输入的不可变副本、版本与哈希在 `inputs/` 和 `baseline.json` 记录。

既有浏览器原型先于本次架构交接，作为行为和状态参考。其页面截图、可运行性或产品代码身份不自动构成正式原生 UI 规格批准。后续顺序为：详细需求交接 → 本架构审阅/技术风险闭环 → UI 规格规划 → 前后端可验证增量。架构或需求改变时，受影响的 UI 状态重新核对。

本会话未暴露 architecture_mcp、workflow_mcp，因此无法调用规则、模板、get_stage_handoff、get_coding_handoff 或阶段门禁。本目录使用自有格式记录交接，不声称通过这些工具，也不自行猜造其正式清单 Schema。工具可用后应依据实际模板导入；不能把本文件的人工核对替代工具门禁。

产品原型代码归属 product，按用户最新规则以可运行和约定场景为准，不要求研发质量门禁。本次没有改动原型代码或其归属；未来正式前后端/核心代码按 engineering 登记并执行 coding_mcp。混合交付按实际文件与责任分别列出，不能把正式研发实现标成产品代码以免除检查。

## 2. 首要技术验证 G0

G0 只做有界、可丢弃或转正的技术验证，不扩展产品功能。每项先冻结源提交/依赖/设备/工具版本，再保留脚本、输入、构建日志、产物哈希、截图或运行追踪以及结论。当前所有条目均为 planned。

|ID|验证内容与最小产物|通过条件|失败处置与影响|
|---|---|---|---|
|SP-01|Android 本机 OpenCode：一个会话、两次领域工具调用、一次取消、一次进程重启恢复|App 私有环境启动；无远端 Agent 代替；能通过工具桥读/提案/提交；通用写文件/shell/间接绕过被拒绝；日志/会话无 Key|检查锁定运行时/原生依赖，给出有界适配补丁与维护成本；仍失败则阻塞 Android AI 集成，向产品/用户反馈，不自行改为云 Agent|
|SP-02|C++ native/WASM：同一类型系统、事务校验和图 corpus；最小 sprite/输入/音频/碰撞样例|规定结果一致；记录浮点差异、异常、内存、启动和性能；选择首个渲染/物理/音频库|调整基础库或平台桥；不能通过另写一套 JS 玩法消除失败|

|SP-04|微信、抖音分别最小运行包|各自在对应开发者工具及实际宿主真机运行 WASM、画面、输入、音频、存储、WSS/HTTPS和生命周期；记录最低版本/限制|将未知能力列为 unsupported，提出平台桥/网关/受影响节点方案，交产品确认范围变化|

SP-01/02/03 是共同关键路径。SP-04 的两个目标可各自验证；一个通过不能代表另一个。SP-05 可与技术运行时验证独立推进。开发并行上限取决于真实人员；每名实现者同时一个主要增量，跨模块同时最多两个待集成变更，避免多人改同一契约。

## 3. 进入正式开发的 G1 条件

以下条件不是本轮已满足的结果：

1. 需求输入及本架构版本被冻结，产品负责人确认范围和验收口径；架构评审确认接口、数据和安全决定。人员审批绑定完整版本和 baseline SHA-256。
2. SP-01/02/03/05 有实际结论；未通过项明确阻塞范围。两小游戏即使尚未验证，也不能在未完成 SP-04 时交付对应发布能力。
3. 冻结 Android 最低系统/ABI、桌面支持矩阵、浏览器/WebView、小游戏宿主版本、基准设备及各样例规模；没有这些信息的性能数字只是目标。
4. UI 设计接收当前需求与架构输入，并建立规划快照；使用 design_mcp 的 planning 检查，不要求不存在的构建截图。
5. architecture_mcp 的 get_coding_handoff 返回 ready_for_coding=true，workflow_mcp 前序交接与当前阶段记录满足门禁；未连接工具时如需开展研发，须由用户明确决定例外，不假称门禁已过。

G0 的受控技术验证可先进行。本轮用户只要求设计架构，尚未实施这些验证或功能开发。

## 7. 架构决定及变更影响

|决定|采用的方案与替代取舍|影响与再评审触发|
|---|---|---|
|ADR-01 项目唯一来源|SQLite事务权威+资源仓；未采用松散JSON直接写入或实时CRDT|引入迁移/恢复责任；多人同时编辑成为真实需求时再评审并发模型|

|ADR-04 本机Agent|上游OpenCode+受限领域桥；未采用重写内核或默认云Agent|Android运行时移植和上游升级成本；未通过SP-01由产品/用户决定范围变更|

|ADR-08 专业功能渐进实现|保留完整需求，按可玩样例扩节点和编辑器|不以排期删范围；增加新类型/目标时更新依赖、测试、预算和UI状态|
|ADR-09 开源与商业服务|GPL公开创作核心/运行器，本地闭环可用；独立私有平台API；用户游戏允许闭源商用|新增权利/依赖审核、例外文本、贡献规则与运行时源码交付；具体GPL版本、接口许可建议及例外需确认后再发布|

Qt表现层、图形/音频/物理库、平台后端Go建议仍为proposed，M0收集证据后形成最终ADR；这些技术建议不冒充已批准决定。改变底层技术时须重新估算构建、许可证、跨目标和团队维护成本。

CHG-001：用户追加GitHub/GPL及开闭源划分要求，并确认用户游戏可闭源商用。范围影响为公开/私有代码依赖、运行时/模板许可和源码交付；设计影响为许可/源码入口与来源提示；测试增加SP-08及四目标许可追踪；成本增加权利清查、法律审阅与社区贡献管理；排期尚无人员/数据，不编造天数；发布前产品基线与UI/研发交接应纳入本变更，不覆盖原需求决定。

## 8. UI与研发的具体交接

UI接收：当前需求状态库存、简易/高级同源规则、异步任务与错误恢复、能力/费用的可见反馈、按对象定位诊断，以及Android/Qt输入差异。UI原型和状态ID必须与产品验收绑定。UI规划完成后用design_mcp.inspect_handoff的planning阶段检查，并保存design_plan快照；正式开发后再对最终构建逐页截图比较。

研发接收：本版CONTRACTS中的领域契约、模块依赖、M0/M1验收、禁止旁路项目写入、数据迁移/回退和预算。前端不自行补造业务规则，后端不自行拆微服务；疑问由架构角色回答并记录决定。如果架构回答涉及业务范围，再归product/user。

发布前预声明engineering质量报告路径，例如 `.quality-mcp/engineering/M1/raw-report.json`，报告版本对应最终增量，owner为该增量研发负责人；实际人员待分配。不得预填报告哈希或伪造文件。完成审批后运行最终coding扫描并保存原始报告，报告目录须被质量工具排除；扫描后不修改被绑定清单。UI还要满足最终构建设计门禁，产品/架构/流程分别执行对应累计阶段检查。

本轮可以核对：文档文件存在、链接有效、输入副本/哈希、契约/模块/验收映射、Q-001写回与独立维度的扩展决策。不能据此证明性能、安全、恢复、真机、引擎或供应商可用性。

尚缺：MCP正式模板及门禁、人员基线审批、冻结目标环境、G0全部运行证据、正式UI规划快照、各增量实际测试与工程质量报告。当前 `ready_for_coding=false`，没有将这些缺口伪装为通过结果。
