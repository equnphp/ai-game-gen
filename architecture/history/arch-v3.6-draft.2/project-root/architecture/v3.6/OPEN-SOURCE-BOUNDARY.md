# GameGen 开源与闭源边界方案

版本：`arch-v3.6-draft.2`。日期：2026-11-14。用户要求发布到 GitHub，开源协议采用 GPL；并已在当前架构会话确认“允许用户生成的游戏闭源商用”。本文件将此作为架构约束，不等同于已完成许可证法律审查或已发布仓库。

## 1. 推荐的授权组合

建议 GameGen 编辑器与核心代码采用 **GPL-3.0-only**。运行时、游戏壳及确实复制到游戏产物的自有模板，再附加经过法律审阅的 **GameGen Runtime/Export Exception**，放行独立游戏内容与运行时组合的闭源商用。版本后缀 only 是本方案建议，用户目前确认的是 GPL 与游戏闭源商用目标；正式发布前应确认具体许可证版本和例外文本。

公共协议定义、数据 Schema、供独立服务使用的轻量 SDK 建议单独采用 **MIT**，以便公有客户端、闭源平台及第三方自建服务互通。该范围只包含接口与独立 DTO/客户端代码，不包含文档事务、图编译器、VM 或引擎实现。这是有意声明的目录例外，项目主体仍为 GPL；若希望这些目录也坚持 GPL，应改成明确的接口使用附加许可并另行审阅，不能直接把 GPL 实现复制进闭源平台。

GPLv3 第7节允许权利人给予额外许可；这类例外应覆盖明确文件和场景。运行时例外需要自己的措辞，不能直接套用只为 GCC 编译流程定义的例外。[GPLv3 第7节](https://www.gnu.org/licenses/gpl-3.0.html#section7)、[GNU 运行时例外说明](https://www.gnu.org/licenses/exceptions.html)。

这份文件给出授权目标和技术边界。正式 LICENSE、例外法律文本与贡献协议需在确认权利链后审阅，不将本设计说明当成已生效的许可。当前没有给项目源文件批量改许可证，也没有创建 GitHub 仓库或推送。

## 2. 公开部分：可以独立使用的完整创作工具

|模块|公开范围|建议许可|
|---|---|---|
|Android / Qt 编辑器|界面、项目管理、地图/图/动画等编辑器、四语、诊断与恢复|GPL-3.0-only|
|Document/Transaction/AuthoringCore|Schema实现、事务、历史、迁移、资源引用与导入校验|GPL-3.0-only|
|GraphCompiler / 图 VM / RuntimeCore|节点语义、组件、渲染/物理/音频接口及自有实现|编辑/编译部分GPL；进入成品的运行部分GPL+运行时例外|
|目标适配与本机构建|H5/WASM、WebView壳、微信/抖音平台桥、本机包生成和签名工具|工具GPL；复制进游戏的自有运行桥/壳/模板按例外清单|
|AgentBridge / OpenCode适配|受限领域工具、会话恢复、BYOK连接、MCP与Skill管理、权限|自有代码GPL；上游代码保留原许可|
|游戏权威运行器|无界面Runtime、服务端图执行、房间/地图宿主及基础自托管脚本|运行器GPL+游戏运行时例外；通用管理工具GPL|
|服务接口|公开API、项目格式、节点描述Schema、最小独立SDK/DTO|建议MIT，排除任何GPL核心实现|
|本地样例与测试|可玩模板、测试corpus、开发构建与说明、mock服务|代码GPL或相应运行例外；美术/音频逐项单列许可|

社区版本应能本地创建、手工编辑、保存、试玩、接自带模型/MCP/Skill，并在构建组件齐备后导出。官方云端积分/媒体/托管服务可以缺省关闭，不能把本地核心依赖做成只有私有仓库才能补齐的二进制。

所有被分发到用户设备的官方编辑器补丁原则上回到公开核心。官方版的云服务入口和客户端协议代码公开；API密钥、额度、供应商价格和服务策略在服务器执行。不能把支付判断、秘密Key或风控当成藏在GPL客户端中的闭源模块。

## 3. 私有部分：独立的官方商业服务

|部分|保留私有的内容|对外边界|
|---|---|---|
|平台模型网关|供应商账户、路由/成本策略、限额、容灾、官方服务质量配置|公开HTTPS API；客户端可换成BYOK或自建兼容服务|
|积分/订单/结算|账户账本、套餐、付款渠道、对账、退款、风控与审计|任务/报价/结算API；不把密钥或规则实现在客户端|
|云媒体任务|供应商编排、官方提示/工作配方、队列、结果交付、内容处理|独立媒体任务API；本地文件导入不依赖服务|
|官方托管控制台|租户管理、游戏服调度、配额、备份运维、监控、客服与运营|管理公开游戏运行器的进程/容器和业务API；不链接GPL运行库|
|资源商城|商品/授权/结算系统、商业素材、供应商合同与私有目录|素材和授权凭证交付；不将商业素材混入GPL示例目录|
|生产基础设施|账号/证书、部署参数、告警、内部运营工具和数据|私有仓库也不提交真实秘密；配置与凭据分别管理|

私有平台采用独立代码实现和独立部署，与GPL客户端/游戏运行器通过版本化业务API交互。它不能 import/link GPL核心库、拷贝图VM/事务代码，或通过共享内存/内部对象ABI组成闭源扩展。把文件放另一个仓库、改为动态链接或单独进程都不自动解决衍生/组合程序问题；需按实际耦合审查。[GNU 关于插件与组合程序的解释](https://www.gnu.org/licenses/gpl-faq.html#GPLPlugins)。

这个划分适合模块化单体：`gamegen-cloud` 内的网关、积分、媒体和运营是一个业务系统的模块，后台任务可用worker；游戏权威运行器由于隔离和资源配额单独执行。开源边界不要求把每个模块拆成微服务。

## 4. 用户游戏与运行时例外的目标

用户已选择：独立游戏内容和业务工作流可以闭源商用。建议例外覆盖以下目标，交由法律审阅形成正式条款：

1. 用户独立创作的地图、关卡、图片、音频、剧情、表格、工作流与对应IR，可自行选择许可；不因使用编辑器或标准节点被自动纳入项目GPL。
2. 允许这些独立内容与获准RuntimeCore/WASM、WebView壳、小游戏运行桥及无界面游戏运行器组合分发，包括付费和闭源发行。
3. GameGen运行时本身及其修改继续遵守对应GPL源码义务。产品包内给出运行时版本、许可、第三方声明与该版本源代码获取方式；用户无须因此公开自己独立的业务工作流和素材。
4. 例外不覆盖把编辑器、编译器或核心引擎修改封装成闭源“高级插件”，也不允许从开源核心拷贝实现后宣称是独立游戏内容。
5. 只有有权授权的自有代码适用。第三方GPL库若无兼容例外，不能由我们代为豁免；进入游戏产物的依赖和模板必须逐项确认。

使用GPL工具生成的输出通常不因工具许可自动变成GPL；本项目还会把运行时代码复制/组合进APK、H5和小游戏，所以需要对这部分明确授权。工作流可执行并不意味着可以一概当普通无版权数据处理。[GNU 关于生成输出的说明](https://www.gnu.org/licenses/gpl-faq.html#WhatCaseIsOutputGPL)。

不建议用“你发布的游戏全部必须GPL”作为默认规则，会改变当前用户已确认的商业目标。也不建议为了闭源游戏给整个编辑器加宽泛链接例外，导致核心改版的回馈边界失去意义。

```text
GitHub public: gamegen/

  apps/qt-editor/            GPL
  core/document/            GPL
  core/transaction/         GPL
  core/authoring/           GPL
  compiler/                 GPL
  runtime/                  GPL + runtime exception（明确清单）
  server/game-runner/        GPL + runtime exception（明确清单）
  targets/                  工具GPL；运行模板按明确例外清单
  assistant/                自有GPL，上游原许可
  contracts/                建议MIT的独立接口/SDK
  examples/ tests/ docs/     分别标明代码、素材和文档许可
  LICENSES/                 GPL正文、正式例外、第三方许可
  LICENSE-MAP.json           文件/组件到许可、权利人、用途的映射
  THIRD-PARTY-NOTICES
  CONTRIBUTING.md

Private: gamegen-cloud/
  gateway/ billing/ media/ operations/ marketplace/
  contracts-client/         只使用获准公共契约与独立实现
  migrations/ tests/

Private: gamegen-ops/
  deployment/ observability/ runbooks/
```

目录是建议目标，不是当前已迁移的工程。公开仓库必须能自行构建其公开产物；私有仓库依赖公共契约，公开核心不反向依赖私有实现。不得用`.gitignore`隐藏同一公开Git历史中的秘密或私有模块；当前工作区还不是Git仓库，正式初始化时从审查后的文件白名单构造公开历史。

LICENSE-MAP建议记录path/component、copyright holder、outbound license、exception reference、third-party origin、是否进入编辑器/游戏/服务器、source package和审查状态。没有权利依据的文件先隔离待审，不凭目录名称批量重标GPL。

## 6. 发布、社区贡献与商业边界

每次公开发行把二进制、精确对应源码、构建/安装脚本、依赖锁定及第三方声明绑定同一release。普通GitHub默认分支链接不能代替“这个发行包对应哪份源码”的明确记录。GPLv3在适用情况下还要求安装信息，不能在官方硬件或签名流程中随意增加限制。[GPLv3简明指南](https://www.gnu.org/licenses/quick-guide-gplv3.html)。

OpenCode当前仓库标MIT，Qt各模块及其依赖可能有不同许可；必须按锁定版本保留原通知和义务，不能仅用顶层GPL覆盖。模型权重、字体、图标、示例素材与生成内容的可分发权也逐项核对。[OpenCode许可](https://github.com/anomalyco/opencode/blob/dev/LICENSE)、[Qt许可说明](https://doc.qt.io/qt-6/licensing.html)。

贡献流程建议采用DCO确认来源，并明确本项目GPL及相关附加许可适用于贡献。DCO本身不自动授予任意商业重授权权利。若未来要“GPL+闭源商业授权”双许可，应提前准备恰当的贡献授权/权利安排；不能收到社区GPL贡献后再假设有权闭源销售该贡献。正式例外所覆盖文件的贡献也必须包含该许可权限。

GPL允许商业使用、收费与合规再分发，不能附加“禁止竞品/禁止商用”仍称原版GPL。普通GPL未把单纯网络使用等同于分发；因此不能承诺竞争者做SaaS一定必须公布服务端修改，也不自动切换用户指定的GPL为AGPL。[GPLv3正文](https://www.gnu.org/licenses/gpl-3.0.html)。

商业收入建议来自官方AI/媒体用量、云游戏托管、备份协作、付费素材与支持。品牌和官方认证用商标政策管理，社区分叉的GPL权利与“冒充官方”分开处理。闭源私有部署版本若包含GPL组件，交付客户时仍按实际组合与分发义务审查，不能仅凭签商业合同关闭源码。

## 7. 执行顺序、成本和验收

1. **权利清查**：逐文件确认自有/雇佣/外包/贡献/复制来源，扫描全部Git历史（建库后）、图片、字体、模型及样例。产物为依赖和权利清单，当前尚未完成。
2. **批准授权方案**：确认GPL具体版本、公共契约MIT例外范围、运行时例外法律文本与贡献规则；当前已确认的是GPL方向和游戏闭源商用目标。
3. **拆清模块**：公开客户端/核心/本地构建/运行器完整可构建；私有平台不导入GPL实现。测试关闭官方服务后本地与BYOK创作闭环。
4. **发布物检查**：GPL/例外/第三方通知、源码包、构建说明、运行时许可证入口、sourceRef随每个目标产物验证。商业素材和秘密不进入公开包。
5. **GitHub发布**：准备公开文件清单、仓库健康文件、CI和首次release；用户确认具体可审阅发布内容后再执行公开动作。

新增成本是依赖许可筛选、运行时源码交付、例外法律审阅、贡献权利管理和公开/私有边界回归；不根据文档长度估算工期。不得为了“兼容GPL”删除第三方版权通知、误标许可或隐藏必须交付的源码。

本方案验收：公开仓库从干净环境能构建并完成本地创作/导出样例；不依赖私有头文件或秘密包；私有平台不链接或复制未获许可的GPL核心；用户独立游戏可按批准例外闭源商用；四目标都能定位随包运行时的对应源码与许可。所有这些均为待验证目标，当前没有运行结果。
